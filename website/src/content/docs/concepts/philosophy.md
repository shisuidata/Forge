## 四个核心信念

### 1. 约束是自由的前提

LLM 的错误率与输出空间大小正相关。让 LLM 在无约束的空间里直接写 SQL，等于让它在无限多的错误可能性里随机游走。

Forge 的做法是大幅收窄输出空间：

- 动态 Schema 对多数表名/列引用提供枚举约束
- JOIN 类型必须显式选择，不存在默认的无类型 JOIN
- `filter` 和 `having` 分离为独立字段

这些保证只在 Provider 严格执行动态 Schema 的受约束字段上成立；表达式透传、兼容降级、业务语义和算法选择仍需 Compiler、Lint、审核与测试继续兜底。

### 2. 意图与执行分离

```
LLM 负责：理解意图 → 生成 Forge JSON（语义层）
编译器负责：Forge JSON → SQL（执行层，确定性）
```

这个分离意味着：

- **可审计**：用户审核的 SQL 和实际执行的 SQL 是同一份
- **可调试**：SQL 出错，可以精确定位到某段 Forge JSON
- **可升级**：换更强的 LLM 不需要动编译器；优化编译器不需要重新训练模型

### 3. Registry 是组织的数据资产

Registry 不是静态的 schema 文件，它是组织知识的沉淀：

- **结构层**（`forge sync` 自动生成）：表结构、列名、低基数枚举值
- **语义层**（对话式维护）：复购率 = 下过 >=2 次订单的用户 / 下过 >=1 次订单的用户

用得越多，Registry 越准确，错误率越低。**这是一个正向飞轮。**

### 4. 编译器修复优于 Prompt 修复

当模型的语义意图是对的，只是 DSL 格式稍有偏差：

- **Prompt 修复**有蝴蝶效应，经常修好一个问题破坏另一个
- **编译器修复**是确定性的，不影响其他路径，测试可覆盖

14 个 `_coerce` 修复，每一个都来自真实失败案例。单次影响最大的改进是一个编译器修复（Case 39：3.0 -> 9.0），而不是任何 prompt 改动。

## 工程洞察

**Alias 作用域是 SQL 的暗礁。** SQL 标准不允许在同层 SELECT 中引用同层定义的 agg alias。解决方案：`_expand_aliases()` 在编译前将 alias 替换为完整表达式。

**新能力文档导致过拟合。** 每向 prompt 添加新能力说明，模型就有过度使用的倾向。加了 CTE 文档后，简单 GROUP BY 也被包成 CTE。对策：每个新能力必须配一个「何时不用」的反例。

**语义消歧库是无损提升。** 在 LLM 调用前注入澄清，不改核心 prompt，不增加 API 调用。J -> J+Sem 提升了 0.17，编译失败率从 0.5% 降到 0.0%。

## 正在思索中

> 这一节是诚实的自我质疑，不是结论。

GLM-5（强推理模型）的测试数据打了一个问号：Forge 74.3% vs 直接 SQL 74.4%，几乎相同。而 MiniMax（中等能力模型）的数据支持 Forge 的逻辑：65.0% vs 57.5%，差距 +7.5pp。

这指向一个不舒服的假说：**当模型足够强，"生成错误"这个错误类型本身就在萎缩。**

### 什么还成立

思考之后，有几件事我们认为仍然成立，与模型能力无关：

1. **Registry 语义层的价值**——"复购率"的分母定义是业务问题，再强的模型也无法凭空知道
2. **审计链的价值**——用户审核的 SQL = 实际执行的 SQL，这在企业场景里是硬需求
3. **弱模型场景仍大量存在**——私有化部署的现实是许多团队用本地中小模型

### 还不清楚的事

- 如果基础模型持续变强，价值主张是否应该从「DSL 约束」转向「Registry + 审计链」？
- DSL 是否应该变得更薄，只保留语义消歧层？

**这些问题目前没有答案，项目正在主动寻找。**
