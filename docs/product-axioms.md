# Forge 产品公理（Product Axioms）

> 状态：已确认的长期产品约束 · Last updated: 2026-08-24
>
> 本文不是功能清单，也不证明 Forge 必然演进为通用 AI Infra。它定义后续产品、架构和商业决策不得轻易违反的第一性原则。完整论证、反证与待验证假设见 [`ai-native-enterprise-thesis.md`](ai-native-enterprise-thesis.md)。当前目标架构见 [`platform-architecture.md`](platform-architecture.md)。

## 1. 第一性问题

Forge 长期面对的根问题不是“如何让模型更会写 SQL”，也不是预设“企业需要一个统一记忆系统”，而是：

> **一个概率性的机器，如何在不拥有最终责任能力的前提下，安全参与组织的认知、决策和行动？**

数据任务是当前最适合验证这一问题的场景：它同时包含事实、语义、权限、推理、审批、执行、成本、责任和审计，而且结果可以复算。

## 2. 基本区分

后续设计必须保持以下对象分离：

- **Source**：原始来源，例如数据库、文档、消息、网页和业务系统。
- **Event**：实际发生过的对话、操作、调用和状态变化。
- **Claim**：人或 Agent 对世界提出的主张，未必为真。
- **Evidence**：支持或反驳 Claim 的可追溯证据。
- **Knowledge**：在明确范围内经合法流程确认、版本化的信息。
- **Decision**：有决策权的 Principal 对明确对象作出的选择。
- **Action**：机器或人实际执行的操作。
- **Memory**：跨任务保留的信息资产，不等于全部原始数据。
- **Context**：为某次任务按目的、权限和预算编译出的最小充分信息。
- **State**：任务当前进度和运行状态，不应与长期知识混为一体。

## 3. 认识与证据公理

### A1. 信息没有脱离上下文的业务意义

重要信息必须能够回答：它是什么、来自哪里、何时产生、适用于哪里、由谁确认、是否仍然有效。

### A2. 模型不是组织权威来源

模型可以生成、归纳和提出 Claim，但不能自行决定组织事实、业务口径、权限和最终行动。

### A3. 没有 Provenance 的内容不得表示为已确认事实

任何关键结论、知识和行动依据都必须能追溯到独立来源；模型生成内容不得通过循环引用获得虚假的事实地位。

### A4. 事实、主张、推断、决策和承诺必须分型

对话中出现一句话，只能证明该表达曾经发生；它不能自动成为个人长期偏好、团队规则或组织正式决定。

### A5. 冲突是一等对象

组织中允许多个有范围的 Claim 长期并存。系统应暴露冲突、作用域和决策权，不能静默覆盖或用单一摘要压平分歧。

### A6. 时间是事实的一部分

知识、权限、Mandate、证据和决策必须支持有效期、过期、替代和历史回放；旧信息不能因语义相似而无条件进入新任务。

## 4. 身份、权力与责任公理

### A7. 任何组织行动都必须归属于 Principal

Agent 不能成为最终责任主体。每次组织行动都必须能追溯到 Human、Team 或 Organization Principal。

### A8. Agent 权限来自有界委托

Agent 的有效身份由 `Principal + Mandate + Task + Policy` 构成。Mandate 至少约束目的、能力、资源范围、预算、有效期、审批和是否允许继续委托。

### A9. 权限不得从自然语言中推断

Prompt、对话、模型结论和渠道传入的裸 `user_id` 都不能建立权限。授权必须由可信身份和服务端 Policy 裁决。

### A10. 决策权与执行能力分离

能提出建议不等于能批准，能调度任务不等于能执行副作用，能执行工具不等于能定义组织真相。

### A11. 审批必须绑定精确且不可变的 Action

Action、数据源、权限上下文、关键版本或风险发生变化后，原审批失效。批准模糊目标不能被解释成批准任意后续执行。

### A12. 高风险副作用不得无边界重放

崩溃、超时和重试不能导致 SQL、写操作、发布或外部通知被盲目重复执行；必须使用幂等、lease、fencing、补偿或人工恢复。

## 5. Context 与 Memory 公理

### A13. 记忆属于 Principal，不属于模型或单个 Agent

更换模型、Agent 和渠道不应导致正式组织资产丢失，也不应让某个模型的隐藏状态成为长期真相源。

### A14. Context 采用最小充分原则

Agent 不需要“全部记忆”。每个 Context 必须绑定 Purpose、Principal、Mandate、Task、权限、新鲜度和 Token 预算。

### A15. Agent 可以提出记忆候选，不能自行提升作用域

从对话或任务提取的信息先成为 Proposal。个人、项目、团队和组织范围的提升需要对应权力和审计。

### A16. 遗忘、撤销和过期是一等能力

统一上下文能力如果不能纠正、撤销、软删除、处理过期和停止召回，就不具备可接受的隐私与治理边界。

### A17. 统一的是协议和治理，不预设统一物理存储

数据库、CRM、Git、文档系统和业务系统继续承担各自真相源职责。集中 Memory Store、联邦 Context Plane 或组合架构必须由真实场景验证，不能先验决定。

### A18. 新基础设施不得制造第二套业务真相源

长期上下文服务优先保存来源、Claim、Decision、索引、关系和 Context lineage；需要实时事实时应按权限访问原始系统。

## 6. 协同公理

### A19. 组织不需要完全共识，只需要合法且可执行的一致性

系统应明确事实、假设、决策权、承诺和责任，而不是假设多人和多 Agent 最终拥有相同认知。

### A20. 协同真相源是 Task、Artifact、Evidence、Decision 和 Action，不是群聊

对话是交互方式；计划、依赖、当前状态、批准对象和交付物必须进入结构化、可恢复的工作图。

### A21. 多 Agent 必须证明收益高于协调成本

不得把增加 Agent 数量视为默认优化。只有职责分离、权限隔离、专业上下文或独立保障确有必要时才增加 Actor。

### A22. 人负责目标、价值、权力和最终责任

Agent 适合结构化、检索、验证、执行和维护状态；人应逐步从重复操作转向制定规则、处理例外和承担高风险决定。

## 7. 经济公理

### A23. 优化目标是最低可信结果成本，不是最低 Token 单价

总成本至少包含模型推理、Embedding/Rerank、工具和数据库计算、存储、延迟、人工审核与预期错误损失。

### A24. 每个 Agent 工作流必须有预算和停止条件

Task 必须可限制模型成本、Token、调用次数、重试、时长、工具成本和人工审核；预算不足时不能无限“再想一次”。

### A25. 成本必须可归因

模型、工具和人工成本应能关联到 Organization、Team、Principal、Agent、Task、Stage 和 Outcome，支持预算、配额和价值判断。

### A26. 确定性系统优先于重复概率计算

能由编译器、Policy、Schema、Diff、缓存、状态机或确定性 Renderer 完成的工作，不应长期消耗模型推理。

### A27. Artifact 复用优先于重新理解原始输入

已有、有效且权限一致的结构化结果应被复用；缓存必须绑定 Context、Policy、Registry、权限和必要的模型/执行版本。

### A28. 成本优化不得绕过质量和权限门禁

便宜模型、缓存或自动路由不能降低已声明的证据、Assurance、审批和安全要求。

## 8. 架构公理

### A29. 模型和 Agent Runtime 可替换，组织资产必须可迁移

长期价值应沉淀在 Registry、Policy、Artifact、Evidence、Decision、评测集和失败样本中，而不是绑定单一 Provider 或 Prompt。

### A30. 调度权、执行权和真相权分别归属

Pi 管理任务推进；Forge 管理可信数据执行与否决；正式组织知识由有权 Owner 和治理流程确认。不得重新形成双 Orchestrator 或隐式真相源。

### A31. 新抽象必须由两个真实消费者证明

通用 Memory、Context、Identity、Cost 或 Agent Control 服务，在只有 Forge 一个消费者时优先以明确 Contract 验证；至少出现第二个真实消费者和不可替代价值后再独立服务化。

### A32. 产品必须能够诚实失败

缺少证据、权限、语义、预算、模型能力或安全条件时，系统必须澄清、暂停或拒绝，不能以流畅输出掩盖能力边界。

## 9. 四个长期问题平面

后续长期设计统一用四个平面检查：

| 平面 | 核心问题 | 典型对象 |
|---|---|---|
| Governance | 依据什么、允许做什么 | Identity、Principal、Mandate、Registry、Memory Scope、Policy |
| Coordination | 谁和谁如何完成任务 | Task、Plan、Actor、Artifact、Decision、Handoff |
| Economics | 是否值得以及可以花多少 | Budget、Model Route、Token、Tool Cost、Human Review、Quota |
| Assurance | 是否正确、合法、可信 | Evidence、Evaluation、Approval、Audit、Outcome、Regression |

四个平面必须共同约束 Action，不能各自形成孤岛。

## 10. 当前非目标

本文不构成以下实施承诺：

- 不承诺 Forge 立即成为通用企业 AI Infra。
- 不承诺建设保存全部信息的单一 Memory Store。
- 不承诺让 Agent 成为独立责任主体。
- 不承诺用多 Agent 替代单 Agent 或确定性流程。
- 不承诺替代数据仓库、CRM、ERP、Git、文档和身份系统。
- 不承诺脱离现有企业责任与权力结构。
- 不承诺自动执行所有查询、补查、知识写入和跨系统动作。

## 11. 决策审查清单

新增产品或架构能力前必须回答：

1. 它解决的不可再简化问题是什么？
2. 哪条产品公理要求或禁止它？
3. 谁拥有事实、权限、预算和最终责任？
4. 哪个系统是真相源，是否制造第二份可写事实？
5. 失败会如何传播，是否可停止、回滚和审计？
6. 为什么现有数据库、搜索、RAG、Runtime 或业务系统不能解决？
7. 它是否减少每个可信结果的总成本？
8. 它是否要求客户先完成不现实的组织重构？
9. 如何用实际任务和指标证伪？
10. 如果是通用基础设施，第二个真实消费者是谁？

## 12. 需要持续验证的假设

- 企业是否愿意为“把模糊意图转化为可信行动”建立统一协议和控制层。
- 数据任务上的治理、协同、成本和保障机制能否复用到运营信息、市场情报和跨系统行动。
- 跨 Agent 长期上下文连续性是否需要独立服务，还是现有系统的联邦 Context 足够。
- Data-Team Led / Business Accessible / Agent Native / Human Accountable 是否形成可持续的采用与付费路径。
- 每个可信结果的总成本是否能够被测量，并真正影响模型路由、协作结构和自动化策略。
