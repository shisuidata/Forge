# Forge 商业化推进计划

> 目标：从“可验证的 AI SQL Agent”推进到“可控生产落地”，再推进到“可正式商业交付”。

---

## 当前定位

Forge 现在已经超过原型阶段。基于 2026-05-06 的 Method AF 测试结果，项目已经达到受控生产落地和封闭 Beta 的候选标准。

当前最适合的阶段：

```text
受控生产落地 / 封闭 Beta 前期
```

核心依据：

- DSL、compiler、Registry、lint 的技术路线已经成立。
- large 40 题 DeepSeek V4 Pro Method AF 达到 Case EA(any) `100.0%`、Case EA(all) `92.5%`、Run ACC `97.5%`、编译失败率 `0.0%`。
- SQL 执行安全、审计、部署就绪检查已经有基础。
- 生产 Docker Compose、生产 env 模板、CLI doctor 和部署说明已经补齐。
- 失败归因、Registry 约定、lint 回归测试已经形成准确率闭环雏形。

仍需补齐：

- 真实客户业务域基准。
- Registry 管理 UI。
- 客户级备份、升级、回滚 runbook。
- 真实客户数据库权限和资源隔离落地。
- 多用户和权限体系。

---

## 优先级总览

### P0：真实业务域准确率闭环

目标：

- 每个客户 schema 都有自己的 accuracy suite。
- 高频查询 Run ACC 稳定 `90%+`。
- 核心指标查询 `90%+`。
- 每次失败都能进入 backlog、Registry、lint 或测试集。

要做：

- 每轮 EA 自动生成失败归因报告。
- 失败样本按根因分类：lint 缺失、Registry 缺失、compiler 可兜底、模型推理边界。
- 把可形式化错误转成 lint 或 compiler 规则。
- 把业务口径错误转成 Registry 规则。
- 把已修复失败样本固化成回归测试。

### P0：真实数据库安全

目标：

- 即使应用层出错，也不能写坏客户数据库。

已完成：

- 应用层只读 SQL 校验。
- 行数上限和查询超时配置。
- readiness/doctor 强制检查数据库只读账号确认。
- PostgreSQL/MySQL 只读账号模板。

还要做：

- 客户数据库实际只读账号验收。
- 查询资源隔离或只读副本。
- 敏感表/字段权限控制。
- 审计日志可持久化和可检索。

### P1：Registry 管理产品化

目标：

- 数据团队可以在 UI 里维护组织知识。

要做：

- 指标定义 CRUD。
- 字段约定 CRUD。
- 歧义规则 CRUD。
- 变更审核、历史、回滚。
- 规则影响范围预览。

### P1：规则租户化

目标：

- 把 benchmark-specific 规则转成 dataset/tenant-specific Registry 规则。

要做：

- Registry 规则支持作用域。
- lint 读取当前数据集/租户规则。
- 管理员可以启停、编辑、回滚规则。
- 规则变更能自动触发相关 accuracy suite。

### P1：私有化部署标准化

目标：

- 客户能按文档部署、升级、备份、排障。

已完成：

- 生产 Docker Compose 模板。
- `.env.production.example`。
- 数据库权限模板。
- `/health/readiness` 和 `forge doctor` 交付检查。

还要做：

- 日志、审计、备份、升级文档。
- HTTPS / 反向代理 / 内网网关样例。

### P2：多用户和权限体系

目标：

- 支持团队级隔离和企业内部权限治理。

要做：

- Admin / 普通用户角色分离。
- API Key scope。
- 团队级 Registry 和数据源隔离。
- 审计日志按团队过滤。
- 用户权限和数据源 ACL 联动。

## 近期工程节奏

### 第一阶段：客户基准建设

交付物：

- 客户 schema sync。
- 客户高频问题集。
- 客户核心指标集。
- 每轮 `runs.json`、`ea.json`、`failure_triage.md`。

用途：

- 验证 Forge 是否能在真实业务域稳定工作。
- 判断 Registry 是否覆盖了客户的真实业务语义。
- 将销售演示从“看起来能生成 SQL”改成“这套业务问题准确率是多少”。

### 第二阶段：Registry 管理闭环

交付物：

- 字段约定和指标定义管理 UI。
- 错误反馈到候选规则。
- 管理员确认后写入 Registry。
- 规则变更触发回归测试。

用途：

- 让数据团队能维护组织知识。
- 让准确率随着使用持续提高。
- 降低工程师手写 YAML 的依赖。

### 第三阶段：生产部署包

交付物：

- Docker Compose 生产模板。
- 环境变量清单。
- 只读数据库账号模板。
- 审计和日志配置。
- 备份、升级、回滚文档。

用途：

- 支持私有化部署。
- 降低客户 IT 和数据平台团队的接入成本。
- 让 Forge 真正融入公司内部数据查询流程。

当前状态：

- 生产 Compose、环境变量模板、只读账号模板和 readiness/doctor 已完成。
- 备份、升级、回滚 runbook 仍需补齐。

## 商业化判定标准

### 可进入受控 PoC

- 高频查询 Case EA(any) `75%+`。
- 编译失败率接近 `0%`。
- SQL 默认人工审核。
- 执行只读、安全、可审计。
- 失败样本能沉淀。

当前状态：已达到。

### 可进入封闭 Beta

- 高频查询 Run ACC `85%+`。
- 核心指标查询 `90%+`。
- Registry UI 基本可用。
- 部署和运维文档完整。
- 多用户基础权限可用。

当前状态：准确率已达到，Registry UI、部署和多用户权限仍需补齐。

### 可正式商业交付

- 客户业务域准确率稳定，Run ACC `90%+`，关键指标查询 `90%+`。
- 客户数据库安全由数据库权限和应用层共同保证。
- 审计、备份、升级、回滚流程完整。
- 线上错误能持续进入改进闭环。
- 有清晰的“不能回答/需要澄清/需要人工审核”机制。

当前状态：更接近；生产部署包和安全检查已补齐，仍需要真实客户业务域验证、Registry 管理 UI、规则租户化和企业权限体系。

---

## 当前最重要的判断

Forge 的商业化关键不是“再加多少功能”，而是：

```text
每一种可形式化错误，都要从模型注意力里拿出来，变成系统约束。
```

Method AF 的结果验证了这个判断：当输出契约、字段约定、排序口径、过滤口径进入 Registry/lint 后，Run ACC 从 `89.2%` 提升到 `97.5%`。
