# 输出契约与Gold使用复核 · 2026-09-06

## 结论

**分析Gold定位错误是正常的开发和调参，不是作弊。** 本轮主动对照两题Gold、原始候选、题意、CSV和实际数据，完成26条有记录的结果查询、5个隔离反例及8份Prompt复原；新增Luna调用0，运行时代码、Gold和原始成绩未改。

| 题目 | 复核结论 | 不应作出的判断 |
|---|---|---|
| md-483 | 我们自动生成的`expected_grain=grouped`与Gold总计冲突；题目确有`per account`，不能只归为模型乱分组。 | 不能用自己的正则标签证明业务必须分组，也不能因此豁免日期错误或改判候选正确。 |
| md-077 | 官方CSV明确支持拼接全名；日期正确的三个候选在当前快照返回相同学生与金额。Gold另有活动参与筛选与DISTINCT。 | 不应把姓名显示方式当成需要打断用户的业务歧义，也不能照抄未有依据的活动关联。 |

## Gold应该怎样使用

先拆解参考解的实体、关联、过滤、粒度、聚合和投影，再对照候选与生成输入，定位问题在生成、上下文、Compiler、输出Contract还是参考本身。可以由此总结通用Prompt、检索、Contract或Compiler改进；开发集就是允许这样分析和调优的。

必须区分三个阶段：**离线诊断可以看Gold；被测候选生成不能偷看本题答案；评分与原始记录不能事后篡改。** 当前500题已是开发／回归集，看Gold后取得的改善如实称为D/R改善，不能冒充独立未曝光H上的泛化。人为反事实必须单独标明，不计为新生成通过。参考SQL也需要核对题意与元数据，不能因为它是Gold便自动把每个JOIN当成通用业务规则。

## md-483：总计和按账户分组

原问题包含“how many loans … per account … were approved”；Gold返回总计。对应冻结上下文却明确带有`result_contract.expected_grain="grouped"`：

- 来源是`forge/benchmark_v2.py::build_result_contract`的`each/per`正则，不是业务确认。
- `services/pi-orchestrator/src/benchmark-runtime.ts`将该字段连同ContextSnapshot送入两臂Prompt。两条件、双臂均带有这一提示；这不是日期处理条件新加的内容。
- 清晰的标量问题“How many loans require payments above 100 dollars per month?”也被该函数标为`grouped`，证明单位表达会触发分组判断。
- 是否由此导致了模型分组，尚未做独立生成消融，不能宣称因果已证实。

公开快照有682笔贷款、682个账户；符合过滤条件的65笔贷款来自65个账户。于是Gold是一行`65`，分组候选是65行账户计数。实际DDL没有`UNIQUE(loan.account_id)`：在保持完整DDL及外键有效的隔离夹具中，账户101有两笔合格贷款、202有一笔，得到总计`3`与分布`[(101,2),(202,1)]`。二者不是单纯排版差异，不能以当前一账户一贷款的偶合消除粒度问题。

严格复核保留**中等置信度的粒度冲突**：`per account`有正面文本依据，两种粒度实质不同，现有数据和未经确认的自动提示不能给出唯一业务口径。真实任务若必须固定唯一粒度、又无已确认语义，再确认总计还是分布；不是让用户确认可从数据发现的日期格式。

人为离线反事实还表明：仅把原Forge基线SQL的两个日期常量改为ISO，保留总计结构，就得到Gold的65；原Direct基线仅改日期仍返回65行分组结果。**这是用Gold分离错因，不是新模型收益，原判分未改。**

## md-077：姓名表示与参考筛选范围

官方`member.csv`明确写着：

> full name is first_name + last_name … Angela Sanders.

这段说明在两条件双臂的指令里。当前三个日期正确候选都得到两名学生及各50的金额，只把姓、名拼为一列；只读的分列反事实与Gold结果一致。原Forge基线仍有独立日期错误，不能被表示差异免责。

Gold还执行`member → attendance → event`内连接，再做DISTINCT。问题、Evidence和相关CSV未提供活动参与筛选要求。两名实际收款成员分别关联14和12个活动，产生26个连接行，再去重为2行；当前快照因此掩盖了额外范围限制。

四个完整DDL、外键有效的隔离反例说明，不能建立通用的“拼接姓名自动等价于Gold”评分规则：

| 反例 | 实际结果 |
|---|---|
| 收款但无活动记录的成员 | 直接收款查询返回2人，Gold只返回参加活动的1人；是筛选范围差异。 |
| 同一成员两笔同金额收款 | 原查询两行，Gold DISTINCT一行；涉及多重集，不只是改列名。 |
| `Mary Ann / Lee`与`Mary / Ann Lee` | 两组姓名都拼成`Mary Ann Lee`，无法无歧义拆回。 |
| 姓名部分为NULL | 原DDL允许；`Sam || ' ' || NULL`变成NULL，丢失已有的Sam。 |

因此，姓名拼接不值得向用户发起澄清；当前信息匹配可以记录，但不能自动重写官方分数或泛化成任意SQL等价。也可以从Gold总结“原始字段投影与展示格式分层”的通用改进，再用姓名、NULL和重复记录对照检验，而不是禁止学习参考解。
