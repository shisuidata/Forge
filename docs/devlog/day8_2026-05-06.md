# Day 8 — 2026-05-06

> 这次没有发明新的 Agent 能力，而是把 Forge 拉回到一个更硬的问题上：它生成的 SQL，到底有多可信？

---

## 做了什么

这一天的主题是**把准确率问题重新工程化**。

前面几天，Forge 已经从一个 DSL 原型逐渐长成了一个可部署产品：Web、认证、Admin、数据库执行、Registry、团队权限、Pipeline 都陆续补齐了。产品形态越来越完整，但这也带来一个风险：功能越多，越容易把最初的问题藏起来。

Forge 最初要解决的不是“能不能聊天”，也不是“页面能不能打开”，而是：

> 自然语言生成 SQL 时，能不能把静默错误尽可能系统性地消灭掉。

所以这次我做的第一件事，不是继续加功能，而是重新测试它。

---

## 一、先把“测试通过”拆开

一开始我差点犯一个很典型的错误：看到 pytest 全绿，就说“测试已经完成”。

但对 Forge 来说，这句话不够准确。因为这里至少有三类测试：

| 测试类型 | 回答的问题 | 这次结果 |
|---|---|---:|
| 单元/API/编译器测试 | 代码分支、接口、编译器行为是否正确 | 241 passed |
| 站点 E2E 测试 | 登录、Chat、Admin 页面是否能走通 | 22 passed |
| Execution Accuracy | 生成 SQL 的执行结果是否等于参考 SQL | 65.0% |

前两类测试说明“系统能跑”。第三类测试才说明“结果是否可信”。

这两件事必须分开。一个 AI SQL 产品完全可能所有页面都正常、所有接口都返回 200，但生成出来的 SQL 悄悄算错。对数据产品来说，后者才是真正危险的失败。

所以这次我单独写了测试报告：

- `docs/test-report-2026-05-05.md`

以后 Forge 的测试结论也应该这样写：工程测试归工程测试，准确率归准确率，不能用一个“测试通过”把问题糊过去。

## 二、GLM-5.1 接上了，但没有跑成

这次原本想用 Z.AI 的 GLM-5.1 做一轮新的准确率测试。

我新增了一个 accuracy method：

- `tests/accuracy/methods/method_v.py`
- 模型：`glm-5.1`
- 接口：`https://api.z.ai/api/paas/v4`
- 协议：OpenAI-compatible

同时修了 `tests/accuracy/runner.py` 的 key 选择逻辑。之前 OpenAI-compatible provider 容易默认回退到 `DEEPSEEK_API_KEY`，这在多 provider 测试里很危险：你以为自己在测 Z.AI，实际可能拿错 key 或打错 endpoint。

现在 runner 会根据 provider 选择 key。Z.AI 只接受：

```text
ZAI_API_KEY
GLM_API_KEY

```

后来确实在另一个项目的 `.env.local` 里找到了智谱相关 key。我没有打印密钥，只做了最小连通性探测。

结果两个 endpoint 都返回了余额不足：

```text
Z.AI endpoint: 429
Insufficient balance or no resource package. Please recharge.

BigModel endpoint: 429
余额不足或无可用资源包,请充值。
```

所以这次 GLM-5.1 的链路已经接好，但 40 题 EA 没有真正跑成。这个结论也要老实写进报告里：不是没找到 key，也不是代码不支持，而是当前账号没有可用资源。

## 三、DeepSeek 当前快照：55.0%

GLM-5.1 受阻后，我先用 DeepSeek 跑了一轮当前代码的 large 40 题。

配置是：

```text
Method U
模型：deepseek-chat
数据集：large 40 题
每题：1 次
retry：2
评估：Execution Accuracy
```

第一次结果：

```text
Case EA: 55.0%  (22/40)
Run ACC: 55.0%  (22/40)
编译失败率: 0.0%
```

这个结果有点刺眼，但也很有信息量。

编译失败率是 0%，说明 Forge DSL、JSON Schema、编译器、retry 这条链路在“生成合法 SQL”这件事上已经比较稳了。模型没有生成一堆不能编译的东西。

但 EA 只有 55%，说明问题已经从“SQL 能不能跑”进入了更深的一层：

> SQL 能跑，但结果不对。

这正是 Text-to-SQL 最麻烦的地方。报错的 SQL 反而容易处理，静默错误才真正危险。

分类里最刺眼的是 TopN：

| 类别 | EA |
|---|---:|
| 排名与 TopN | 20.0% |

也就是说，模型并不是整体都不行，而是在某一种模式上明显摔倒了。

## 四、TopN 的错误，不是不会排名，而是没有过滤

看失败样本后，问题变得很具体。

用户问的是：

```text
每个品类销售额最高的前 3 个商品
```

模型往往已经知道要写窗口函数，也会生成 `row_number()` 或 `rank()`。它不是完全不会做 TopN。

真正的问题是：它生成了排名列，却忘了用 `qualify` 把排名过滤掉。

结果变成：

```text
用户要：每个品类前 3 个商品
模型给：每个品类所有商品，只是多了一列排名
```

这是一个非常典型的 Forge 式问题。

它不是业务逻辑错误。因为“每个品类前 3 个”没有业务歧义。

它也不是算法逻辑错误。因为模型已经知道要用窗口函数。

它是结构性生成错误：意图已经理解了，但少了一个必须存在的结构。

所以这类错误不应该继续留给模型注意力，而应该变成程序规则。

## 五、把 TopN 变成 lint 规则

这次新增了一个 TopN lint。

规则大致是：

```text
如果用户问题里出现“各 / 每个 / 每组 / 每类 / 组内”
并且同时出现“前 N / top N / 排名 / 最高 / 最多 / 最低 / 最少”
那么它大概率是一个组内 TopN 问题。

如果 Forge JSON 里已经生成了 row_number/rank/dense_rank，
但没有 qualify 引用排名 alias，
就触发 warning，让 agent retry。

如果完全没有 ranking window，
也提醒不要用全局 sort + limit 伪装组内 TopN。
```

涉及文件：

- `forge/lint.py`
- `agent/prompt_examples/topn.md`
- `tests/test_lint.py`
- `tests/test_prompts.py`

同时我补了一段 TopN prompt 示例：先聚合成 CTE，再在聚合结果上做 window ranking，最后用 `qualify rank <= N` 过滤。

这个示例不是为了“教模型一点 SQL 小技巧”，而是为了明确 Forge JSON 里表达组内 TopN 的标准结构。

这里还有一个小修正：之前有一条 category lint 过强，会把 window partition 里的 `category_name` 也当成需要补 `category_id` 的场景。这在某些业务系统里可能是合理的，但在当前 EA benchmark 里反而会造成列不匹配。

所以这次把规则收窄：

```text
GROUP BY category_name 时，仍建议带 category_id。
window partition by category_name 时，不强制补 category_id。
```

规则不是越强越好。好的 lint 应该拦住真实错误，而不是把所有“看起来不够严谨”的写法都打成错误。

改完 TopN lint 和 prompt 示例后，重新跑 DeepSeek large 40 题 single-run。

结果：

```text
Case EA: 65.0%  (26/40)
Run ACC: 65.0%  (26/40)
编译失败率: 0.0%
```

和改前相比：

| 指标 | 改前 | 改后 | 变化 |
|---|---:|---:|---:|
| Case EA | 55.0% | 65.0% | +10.0pp |
| Run ACC | 55.0% | 65.0% | +10.0pp |
| 排名与 TopN | 20.0% | 100.0% | +80.0pp |

需要谨慎的是：这是 single-run，模型有随机性，不能把 65.0% 当成长期稳定值。

但 TopN 的提升是可信的。因为它不是“这次刚好运气好”，而是错误类型被明确识别，并且被程序规则拦住了。

这是 Forge 最想看到的优化方式：

```text
发现错误模式
  ↓
把错误模式形式化
  ↓
写成 lint / schema / compiler 约束
  ↓
让模型在约束下重试
```

## 七、这次优化验证了什么

这次真正验证的不是“DeepSeek 能不能多答对 4 道题”。

更重要的是，Forge 的核心路线仍然有效：

> 能被形式化的错误，不要留给模型注意力。

如果一个错误可以被描述成结构缺失，就不要只在 prompt 里写一句“请注意”。Prompt 会被忽略，长上下文里的规则会被稀释，模型会在修复一个问题时引入另一个问题。

但程序约束不会忘。

TopN 缺 `qualify` 就是这样一个错误：

```text
意图：每组前 N
结构：window ranking
缺失：post-window filter
约束：ranking alias 必须出现在 qualify 中
```

这种问题正好落在 Forge 的能力边界内。它不需要模型变聪明，也不需要换更贵的模型，只需要把错误从“自然语言提醒”降级为“程序检查”。

这也是 Forge 和普通 Text-to-SQL 工具的区别。

普通 Text-to-SQL 更像是在赌模型一次写对。Forge 想做的是：让模型先生成一个中间表示，然后用 schema、compiler、lint、registry 一层层把错误空间压小。

## 八、还剩什么

这次优化后，large 40 题 single-run EA 到了 65.0%，但这还不是一个可以满意的数字。

剩下的问题主要集中在几类：

1. **综合复杂查询**：多个 CTE、窗口函数、比率计算、反连接组合在一起时，模型仍然容易漏步骤。
2. **复杂过滤**：有些业务约定还停留在 prompt 或 Registry 文本里，没有被程序化验证。
3. **退款率 / 退货率 / 订单事实表关系**：这类指标需要更清晰的语义层定义，不能让模型猜。
4. **GLM-5.1 对比**：Method V 已经接好，等 Z.AI key 有余额后，需要补一轮同口径测试。

下一步不是盲目加 prompt，而是继续做失败归因：

```text
哪些错误可以变成 lint？
哪些错误应该进入 Registry？
哪些错误属于 compiler 可以兜底的结构？
哪些错误确实是模型推理边界？
```

只有这样，准确率提升才是可解释、可复现、可继续积累的。

## 今天学到的

**第一，测试报告必须分层。**
单测通过、站点 E2E 通过、EA 通过，是三件不同的事。对 AI SQL Agent 来说，最关键的是执行结果正确，而不是接口正常返回。

**第二，编译成功不等于答案正确。**
这次编译失败率是 0%，但初始 EA 只有 55%。这说明 Forge 已经解决了一部分“生成合法性”问题，但还要继续解决“执行语义正确性”问题。

**第三，好的优化不是加更多话，而是加更硬的约束。**
TopN 的问题如果只写在 prompt 里，模型还是可能忘。写成 lint 后，它就成了系统的一部分。

**第四，规则要克制。**
category lint 的收窄提醒我：程序规则不是越多越好，也不是越严越好。它必须精确服务真实错误，否则会把正确答案推向错误。

这次的结论很清楚：Forge 还没到最终状态，但路线是对的。每当一种错误能从“模型注意力问题”变成“程序约束问题”，SQL 的可信度就会往前走一步。
