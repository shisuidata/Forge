前面几天我们已经把 Forge 从原型推到了产品形态：Web、认证、执行、Admin、Registry、权限都陆续补齐。但一个 AI SQL Agent 最终还是要回到同一个问题：生成出来的 SQL，执行结果到底对不对。

1. 重新区分测试口径：单元测试、站点 E2E、Execution Accuracy 不是一回事

3. 用 DeepSeek 跑 large 40 题 single-run EA，得到一个当前快照

## 一、先把“测试”说清楚

一开始我犯了一个很常见的工程错误：看到 `pytest` 全绿，就说测试完成了。

但对 Forge 来说，测试至少分三层：

| 层级 | 测什么 | 这次结果 |
|---|---|---:|
| 后端/API/编译器单测 | 代码行为、接口、编译器、Agent 分支 | 241 passed |
| 站点 E2E | 登录、Chat、Admin 页面导航 | 22 passed |
| EA 准确率 | 生成 SQL 与参考 SQL 的执行结果是否一致 | 65.0% |

前两层回答的是“系统是否能跑”。第三层回答的才是“SQL 是否可信”。

这两个问题不能混在一起。一个系统可以全部单测通过，但 SQL 生成准确率很差；也可以某个页面 E2E 失败，但核心 DSL 编译器完全正确。

所以这次单独写了测试报告：

- `docs/test-report-2026-05-05.md`

这份报告把工程测试和准确率测试分开记录，避免再用“测试通过”掩盖准确率问题。

## 四、TopN 的问题不是 SQL 语法，而是缺少“组内过滤”

看失败样本后，TopN 的主问题不是模型不会写窗口函数。很多时候它已经生成了 `row_number()` / `rank()`。

真正的问题是：它打了排名，但没用 `qualify` 过滤。

结果就是：

```text
用户要：每个品类前 3 个商品
模型给：每个品类所有商品 + 一个排名列
```

这类错误很适合 Forge 的核心思想：不要指望模型每次都注意到，而是把它变成程序规则。

新增 lint：

```text
如果问题是“各/每个/每组...前 N/排名...”
  且 Forge JSON 有排名窗口函数
  但没有 qualify 引用排名别名
则触发 retry
```

同时补了 prompt 示例：

```text
先聚合成 CTE
再对聚合结果 window 排名
最后 qualify rank <= N
```

涉及文件：

- `forge/lint.py`
- `agent/prompt_examples/topn.md`
- `tests/test_lint.py`
- `tests/test_prompts.py`

还顺手收窄了一条之前过强的 category lint：
`GROUP BY category_name` 仍建议带 `category_id`，但 window `partition by category_name` 不再强制要求 `category_id`。因为 benchmark 的 C17/C38 参考答案就是按品类名称做组内 TopN；在这个场景里强推 category_id 反而会让 EA 变差。

这是一个很典型的产品取舍：Registry 约定要服务业务语义，但 benchmark 口径也必须诚实对齐。规则不能因为“看起来更严谨”就到处套。

## 六、这次真正验证的是 Forge 的方法论

这一天最大的收获不是 65.0% 这个数字，而是再次验证了 Forge 的基本路线：

> 能被形式化的错误，不要留给模型注意力。

TopN 缺 `qualify` 不是“业务推理错误”，也不是“算法能力边界”。它是结构性生成错误：

```text
意图：每组前 N
缺失：post-window filter
修复：window alias 必须被 qualify 引用
```

这正是 DSL + lint 能解决的问题。

相比之下，剩下的综合复杂查询更难。它们经常混合：

- 多个 CTE
- 窗口聚合
- 比率计算
- 维度字段歧义
- 反连接条件组合

这些问题不一定能靠一条 lint 解决。下一步需要更细地拆失败样本，看哪些是规则缺失，哪些是真的推理边界。

下一批优化优先级：
